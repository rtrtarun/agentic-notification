# Release 0.36.0

The first versioned release. It brings real sign-in and sign-up, accounts in the Java service, and two published images. The record of the work is [milestone 36](../milestones/milestone-36.md); the running history is [CHANGELOG.md](../CHANGELOG.md).

## Highlights
- **Sign-in first.** The console starts at the sign-in page and uses the service address built into the site. The API key is an "Advanced" option for services, and signing out forgets it.
- **Sign-up with admin approval.** People can ask for an account (`AUTH_SIGNUP=approval`, off by default). A new account is pending, can't sign in or see anything, and an admin approves or rejects it on the Users screen.
- **Accounts in the Java service.** The same sign-in, sessions, roles and sign-up as the Go service, with passwords hashed the same way, so an account made by one signs in on the other.
- **Two published images with versions.** `notification-service` (Go) and `notification-service-java`, tagged with the release, the minor version, `latest` and the commit. `GET /health` returns the running release.
- **A GitHub Release per version**, created by the publish workflow (this one).

## What changed
- **Go:** `POST /api/auth/signup`; `users.status` (`active`, `pending`, `rejected`); a pending or rejected account never gets a session; `PATCH /api/users/{id}` accepts `status`; `GET /api/auth/status` reports `signup`; login answers `403` with `code` `pending` or `rejected`; `/health` returns `version`; one lint finding fixed.
- **Java:** accounts, sessions with CSRF, roles, sign-up, user management and audit; rule changes and manual delivery retries need an admin; `/health` returns `version`.
- **Console:** sign-in and sign-up pages, a pending-approval list with Approve and Reject, real sign-out, and a clear message when the browser does not keep the session cookie.
- **Delivery and CI:** two images built from the `VERSION` file; CI now also runs on `master` and on pull requests into it.
- **Docs:** deployment record (where it runs, secrets and variables, a dated log), runbook entries, feature-flow diagrams, refreshed README.

## Upgrade notes
1. **Database:** the first start adds `users.status` (idempotent; existing accounts become active). Nothing to run by hand. The Java service waits for the Go service's migration; it never migrates.
2. **Deploy a version tag:** point the host at `notification-service:0.36.0`, then check `GET /health` returns `"version": "0.36.0"`. The host is not redeployed by the release; trigger it.
3. **New settings:** `AUTH_SIGNUP` (`off` or `approval`), `APP_VERSION` (set by the image build). Java also reads `AUTH_BOOTSTRAP_EMAIL`, `AUTH_BOOTSTRAP_PASSWORD`, `AUTH_SESSION_TTL`, `AUTH_COOKIE_SECURE`, `AUTH_COOKIE_SAMESITE`.
4. **Console on another site than the service:** set `AUTH_COOKIE_SAMESITE=none` (it forces `Secure`), or sessions will not stick.
5. **With a pooled Neon database,** use the direct host and `binary_parameters=yes`.

## Behaviour changes to know
- The console's first-run flow no longer asks for an API key; use an account (or **Advanced**).
- Signing out forgets an API key held in the tab.
- In the Java service, a signed-in member can read but not change rules or retry deliveries; the API key still can.
- `/health` has a new `version` field (extra field; existing checks that read `status` are unaffected).

## Checked, and not checked
- **Checked locally:** Go full suite and integration tests against PostgreSQL 16, Java `mvn verify` (156 tests, 170 with PostgreSQL, 95.2 percent), 238 web tests and the production build, the 10-file contract on both services, both images built and reporting `0.36.0`.
- **Not verified:** the publish and release workflow itself, sign-up and approval in a browser against the live service, and the cross-site cookie in browsers that block third-party cookies.

## Known issues
No ingestion rate limiting; a critical event can be sent twice if the same delivery arrives twice at once; per-address limits are shared by everyone behind a proxy; an approved member sees every event (one workspace); no email verification or password reset yet. The full list is in [implementation-sync.md](../implementation-sync.md).
